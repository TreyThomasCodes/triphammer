# Review loop

Work is done when checks pass and an independent reviewer has no blocking findings, not when the code compiles.

1. **Check.** The commands are the project's `checks` in `.triphammer/project.json` (`bin/README.md` "The project file"). Run the focused tests first (`checks.focused`, its placeholders filled in for the area you changed), then the whole suite (`checks.suite`). Before a pull request, run the full gate (`checks.gate`; `AGENTS.md` "Checks" says what it adds and whether CI runs it). A check you could not run is explained in the pull request comment (step 6), not in the description.
2. **Self-review.** Go through the `triphammer:review-checklist` skill against your diff first. Then read your full diff against `AGENTS.md` and the rule documents it points to. Then review the changed call path for simplicity: remove duplicated mechanics, speculative construction paths and indirection that adds no information. When you move or rewrite an existing rule, list anything about it that looks wrong (a holiday that can be selected, an unhandled case), keep the existing behavior unless it is plainly a bug, and put the list under **Decisions for the owner** in the pull request comment; the owner reverses one with a review rather than being asked first.
3. **Independent review.** Spawn a fresh `triphammer:reviewer` subagent that did not write the code. Give it only the issue number, the base (`origin/main`) and `AGENTS.md`, never your own opinion of the diff. Its agent definition (`agents/reviewer.md` in this plugin) says how it reviews and what counts as a blocking finding.
4. **Iterate.** Reproduce each finding before fixing it, and drop one you cannot reproduce (say why in the reviewer notes). Fix it, rerun checks, and ask for a fresh review. A finding that fits no checklist class and could recur becomes a new class, in `triphammer:review-checklist` or the project checklist as `triphammer:review-checklist` says. After three rounds that still have blocking findings, stop: add the `needs-owner` label to the issue and comment what you tried. A light run (the runner's prompt names `triphammer:builder-light`; `triphammer:ticket-run`, Light runs) hands over instead: it pushes its branch, comments on the issue with what it tried and each finding it could not resolve, adds no `needs-owner`, and ends without a pull request, so the next run takes the ticket with the Opus builder.
5. **Simplify.** Once no blocking findings remain, spawn one more fresh subagent, `triphammer:simplifier`; its agent definition (`agents/simplifier.md` in this plugin) gives its one question and the third-copy rule. This pass never blocks a pull request and is not another review round.
6. **Open the pull request.** It closes its issue (`Closes #N`; CI checks this). The PR description is the squash commit message, because GitHub fills the squash merge from it: 3-6 plain lines on what changed and why, ending with `Closes #N`. Before `gh pr create`, or `gh pr edit` with `--title` or `--body`, run the `humanizer` skill in its embedded mode on the title and description and post what it returns; code spans, paths and the `Closes #N` line stay as they are. The writing rules are stated in the header of the plugin's `hooks/text-lint.py`, the hook that enforces them and refuses the command until the skill has run in the session. Put everything a reviewer needs but `main` doesn't (checks run with results, review rounds, decisions, the cleanup proposals of this session, the `triphammer:merge-policy` tier output) in a PR comment with `gh pr comment`. Then follow the `triphammer:merge-policy` skill.

Something you needed but could not find (a tool, a fixture, a doc) is a harness gap. Do not work around it silently: append a proposal for it to `$TRIPHAMMER_PROPOSALS`, the one-line JSON object `agents/simplifier.md` describes (its `mechanism` names the gap, its `locations` where you needed it, its `fix` what would close it), which the ticket runner files as an issue after the session, and say so in the pull request comment. Never run `gh issue create` for it. When `$TRIPHAMMER_PROPOSALS` is unset, the pull request comment alone carries it.
