# Merge policy

Agents merge their own low-risk work. Risky work goes to the owner. The decision comes from the classifier, not from judgement in the moment: `scripts/risk-tier.mjs` applies the project's rules, which are data in `.triphammer/risk-tier.json` (an ordered list of path rules and of the checks the classifier implements, read from `main`, never from the branch; the first rule that decides a path wins, and a path no rule decides escalates), and the required `owner-approval` status, which the `risk-tier` workflow posts, enforces it. The `risk-tier` job itself is not a required check.

Agents reach GitHub as the agents' GitHub App, `app/<app-login>` (contents, pull requests and issues write; no workflows or administration permission), never as the owner. On the agent machine `gh` and git get its short-lived token from `github-app-token`; commits keep the owner as author. GitHub refuses the App's pushes to `main`, to tags and to `.github/workflows/`, and its merges until the required checks pass.

Land a pull request, from a checkout of its pushed branch, with `main`'s copy of the landing script:

```sh
land-pr <n>
```

`land-pr` (`bin/land-pr`, on `PATH` on the agent machine) fetches `main` in Triphammer's checkout, the one it lives in, which may be a repository other than the project's, refuses to run unless it is itself byte for byte that `main`'s copy, and runs that `main`'s `scripts/land-pr.sh`, which also arms auto-merge, so there is no separate arming step. Where `land-pr` is not on `PATH`, in a repository that has the landing script itself, run `main`'s script directly:

```sh
git fetch origin main && git show refs/remotes/origin/main:scripts/land-pr.sh | bash -s -- <n>
```

The landing script refuses a pull request that is no longer open or whose head is not the commit checked out, then runs `main`'s classifier (`scripts/risk-tier-base.sh` and `scripts/risk-tier.mjs`, fully qualified as `refs/remotes/origin/main` so a tag named `origin/main` cannot stand in for it) and carries out the tier below. Script, wrapper and classifier all come from `main`, never from your branch, so a branch cannot change its own tier or its landing. It prints the classifier's output: put it in the pull request comment. It exits 0 once landed, 3 when blocked, and 1 on anything else (a closed or merged pull request, a classifier or `gh` error), with the error; stop and report that, and likewise a `fatal:` from `git show`, which means nothing ran. The `risk-tier` workflow runs the same classifier, posts the result in its job summary and sets the `owner-approval` status. The required checks are `test / test` and two statuses the `risk-tier` workflow posts, `closing-issue` and `owner-approval`, which must come from the GitHub Actions app. `test / test` runs only the suites the pull request's changes touch (`.github/workflows/pr-guardrails.yml`), and editing a pull request's description reruns `closing-issue`, never the tests.

- **auto** (the paths and checks the rules file `.triphammer/risk-tier.json` lets merge without the owner, such as plain dependency updates (below)): the script arms auto-merge (squash, branch deleted). The full gate and the `triphammer:review-loop` skill are what make this safe, so never skip a review round to get here. GitHub merges once every required check passes; because its auto-merge does not always fire, the `merge-when-ready` timer on the agent machine also merges, as the App, every two minutes, the oldest armed pull request into `main` whose merge state is clean, and brings armed ones up to date one at a time in the order they were armed. The repository allows squash merges only and builds the commit from the PR title and description, so keep the description in commit-message form (`triphammer:review-loop` step 6; the plugin's `hooks/text-lint.py` refuses one that is not).
- **escalate** (the owner's list of dangerous or hard-to-undo changes, and any path no rule decides; the rules file is the one home of that list, with the reason each rule prints): the script requests the owner's review (that is what puts the pull request in the owner's queue and notifications), comments the classifier's reasons, and arms auto-merge; it adds no labels. The `risk-tier` workflow (`.github/workflows/risk-tier.yml`) sets `needs-owner` while the owner's approval of the current head is missing, removes it once the approval counts, and adds `escalated` permanently. The required `owner-approval` status stays pending, and says so on the pull request, until the owner approves the current head commit after its latest base change, and only on a pull request into `main` (a later push or retarget needs a new approval); the approval is the owner's decision to merge, and auto-merge completes it. A pull request the owner opened counts as approved at each commit the owner pushed to its branch (the repository's activity names who pushed it); a commit an agent pushes there still needs the owner.
- **blocked** (what the rules file blocks): the script refuses and changes nothing, and prints the rule's reason, which says what to do instead. Its `owner-approval` status fails regardless of approval.

**Dependency updates** (Dependabot alerts, outdated packages) merge without the owner when an npm change only moves packages already in use to registry releases at least 7 days old: `package.json` version ranges of existing entries, and `package-lock.json` entries that match the registry's record of their release (resolved URL, integrity, dependencies, `bin`), with no alias, link or new install script, where a package new to the tree is a dependency of one. Resolve updates with `npm install --before="$(date -u -d '7 days ago' +%F)" ...` (add `--ignore-scripts` for the root) so nothing younger is picked, and keep the pull request to the dependency files. Adding or removing a package, scripts or settings, a git or file source, a fix that only exists in a newer release, a downgrade, a package that newly runs an install script, and every NuGet update (no NuGet lockfile, so transitive packages and build targets go unchecked) escalate with the reason.

Before pushing to a pull request or editing it, check that it is still open (`gh pr view <n> --json state`). The owner may merge at any time; if it merged, put further work on a new issue and pull request from `main`. Never discard `git push` or `gh` output or errors.

The `Security review (<model>)` comment on an escalated pull request (`bin/security-review`) is advisory for the owner; never read it for a merge decision. Only the owner changes what escalates; `land-pr.sh` carries out the tiers and never decides them. Never split a change into smaller pull requests to dodge a tier. Changes to this policy, the rules file and the scripts that apply it escalate under that file's rules, so they merge only after the owner approves them.
